# 四栏中线拖拽改造方案

## 1. 背景与目标

当前项目在四栏布局下，界面中间存在一根视觉上的竖向分隔线，用于区分左侧两栏和右侧两栏。现在的诉求是：

- 在 `PaneLayout.four` 下，这根中线可以被用户在当前运行时自由左右拖动。
- 在 `PaneLayout.twoH` 下，继续保持左右双栏也可以拖动宽度。
- 本次改造只要求运行时生效，不要求在切换项目、重启应用后记住拖拽结果。
- 不改动现有四个 pane 的业务能力，包括焦点、标签页、文件列表、预览区、搜索、拖放等。

这次改造的重点不是“画一根能拖的线”，而是把主内容区的 pane 布局从静态拼接改造成原生 split 结构，让中线真正成为可拖拽的分隔器。

## 2. 当前实现现状

### 2.1 主窗口当前只有侧边栏层级使用原生 split

`MainWindowView.windowChrome` 当前使用一层 `HSplitView`，左侧是 sidebar，右侧是 toolbar + paneGrid + status bar。

相关位置：

- `Sources/mq-dir/MainWindowView.swift`
- `windowChrome`
- 约 `151-193` 行

这一层 split 已经通过 `SidebarInitialWidthBridge` 和 `SidebarSplitController` 完成了原生 `NSSplitView` 宽度控制与运行时拖拽，因此侧边栏本身是原生可拖的。

### 2.2 paneGrid 当前是静态布局，不是真正的 split

`paneGrid` 目前的实现如下：

- `one`：直接渲染 `paneView(0)`
- `twoH`：`HStack + Divider + paneView`
- `twoV`：`VStack + Divider + paneView`
- `four`：外层 `VStack`，每一行是 `HStack + Divider`

相关位置：

- `Sources/mq-dir/MainWindowView.swift`
- `paneGrid`
- 约 `513-543` 行

这意味着：

- 中间竖线只是 `Divider`
- 它只负责视觉分隔，不负责布局约束
- 用户不能拖拽它改变左右列宽

### 2.3 当前没有主 pane 区域的分割比例状态

当前 `WindowState` 只持久化以下内容：

- `layout`
- `focusedPaneIndex`
- `panes`

相关位置：

- `Sources/mqdirCore/PersistenceService.swift`
- `WindowState`
- 约 `215-266` 行

因此，本次如果只做“当前运行时可拖动”，可以不新增任何持久化字段，这也是本次方案风险可控的关键原因。

### 2.4 项目里已经有可复用的原生 split 先例

除了侧边栏外，单个 pane 内部的预览区也已经使用 `HSplitView`：

- `Sources/mq-dir/BrowserPaneView.swift`
- `content`
- 约 `1103-1111` 行

说明当前工程是接受原生 split 布局方案的，不需要从零探索这条技术路线。

## 3. 改造目标的边界

### 3.1 本次明确要实现的内容

- `twoH` 模式下左右两栏可以原生拖拽宽度
- `four` 模式下中间竖线可以原生拖拽宽度
- `four` 模式下上排和下排共用同一套左右列宽，保证中线垂直对齐
- 拖拽结果只在当前窗口实例生命周期内生效

### 3.2 本次明确不做的内容

- 不持久化左右分割比例
- 不新增设置项
- 不改动 `WindowState` / `WorkspaceState` / `PersistenceService`
- 不处理“三栏布局”扩展
- 不顺手实现“上下中线也可拖动”

## 4. 风险评估结论

结论：**中低到中等风险，可控，适合单次集中改造。**

### 4.1 风险不算大的原因

- 不涉及状态模型和磁盘持久化
- 不涉及文件操作、撤销、标签页模型等核心业务层
- 现有工程已经使用过 `HSplitView` 和 `NSSplitView` 桥接
- 改造集中在 `MainWindowView` 的 pane 容器层

### 4.2 主要风险来源

#### 风险 A：四栏上下两排必须共享同一根中线

如果简单把四栏改成两个独立 `HStack` 或两个独立 `HSplitView`，上排和下排会各拖各的，最终中线不对齐。这是本次改造最核心的结构性风险。

#### 风险 B：pane 最小宽度与内部内容压缩

每个 `BrowserPaneView` 内部还包含：

- 标签栏
- 文件列表列头
- 树形视图 / 列表视图
- 可选预览区

当 pane 被拖得过窄时，可能出现：

- 列头压缩感增强
- 横向滚动更容易出现
- preview 打开时剩余宽度紧张

这类问题通常是 UI 体验风险，不太像崩溃风险。

#### 风险 C：布局切换时的观感

在 `twoH` 与 `four` 之间切换时，因为本次不持久化比例，系统可能回到 `HSplitView` 的默认分配结果。只要布局稳定、不闪动、不破坏内容，就是可接受的。

#### 风险 D：焦点和交互事件

pane 自己有 `onFocus`、拖放、tab 操作、搜索等交互。容器改成 split 后，原则上不应破坏这些能力，但需要在验收时重点验证点击 pane、切换焦点、拖动分隔线后的行为是否一致。

## 5. 推荐的改造结构

## 5.1 推荐方案总览

推荐把主 pane 区域改为以下结构：

- `one`
  - 保持不变
- `twoH`
  - 改为原生 `HSplitView`
- `twoV`
  - 可以先保持现状不变
- `four`
  - 改为“外层一个左右 `HSplitView`”
  - 左列内部用 `VStack` 放 `pane0`、`pane2`
  - 右列内部用 `VStack` 放 `pane1`、`pane3`

这样可以保证：

- 双栏模式拥有真正可拖动的左右分隔线
- 四栏模式拥有一根统一的、贯穿上下两排的中线
- 上下两排天然共享同一套左右列宽

### 5.2 结构示意

当前四栏大致等价于：

```text
VStack
├─ HStack(pane0 | pane1)
└─ HStack(pane2 | pane3)
```

推荐改为：

```text
HSplitView
├─ VStack
│  ├─ pane0
│  └─ pane2
└─ VStack
   ├─ pane1
   └─ pane3
```

注意：外层是左右 split，内部上下仍可先保持静态平均分配。这样正好匹配本次只解决“中间竖线左右拖拽”的目标。

## 6. 为什么不推荐给当前 Divider 直接绑 DragGesture

虽然理论上可以在现有 `Divider` 上叠加 `DragGesture`，再手动维护左右宽度比例，但不推荐，原因如下：

- 现有 `Divider` 只是视觉元素，不是原生分隔器
- 需要自己处理拖动手势、宽度计算、最小值限制、窗口 resize 联动
- 四栏上下两排还要额外做同步逻辑
- SwiftUI 手写比例布局更容易引入边界 bug
- 用户体验通常不如原生 `HSplitView`

因此，本次应优先采用原生 split 方案，而不是“模拟一个可拖 Divider”。

## 7. 详细实施步骤

### 步骤 1：只重构 `paneGrid`，不改业务层

改造目标：

- 只调整 `MainWindowView.paneGrid`
- `paneView(_:)` 保持原样
- `BrowserPaneView`、`PaneTabsViewModel`、`FolderBrowserViewModel` 等不做业务逻辑变更

好处：

- 把影响面锁定在布局层
- 方便对比改造前后行为差异

### 步骤 2：把 `twoH` 从 `HStack` 改为 `HSplitView`

目标：

- `paneView(0)` 与 `paneView(1)` 由原生 split 管理
- 给左右 pane 设定适度的 `minWidth`
- 保持 `maxWidth/maxHeight` 的现有扩展行为

建议：

- 最初先不给复杂的宽度控制器
- 先依赖 `HSplitView` 默认拖拽行为
- 若宽度塌陷明显，再补充列级别最小宽度约束

### 步骤 3：把 `four` 改为“外层 HSplitView + 内层 VStack”

目标：

- 左右列共享同一个 split divider
- 左列包含 `pane0`、`pane2`
- 右列包含 `pane1`、`pane3`
- 列内部上下之间继续保留 `Divider`

建议结构：

```swift
HSplitView {
    VStack(spacing: 0) {
        paneView(0)
        Divider()
        paneView(2)
    }
    VStack(spacing: 0) {
        paneView(1)
        Divider()
        paneView(3)
    }
}
```

### 步骤 4：为左右列设置合理的最小宽度

这一步是否需要做，取决于第一轮效果。

建议原则：

- 不是给内部每一个子视图都加很多约束
- 而是先给左列容器和右列容器设置一个基础 `minWidth`
- 例如按 `BrowserPaneView` 当前最窄可接受宽度预留空间

注意：

- 本次不追求绝对完美的极窄布局观感
- 只要不出现明显错误、内容不完全不可用即可

### 步骤 5：保留 `twoV` 现状

`twoV` 这次可以不动，原因是当前需求只关注：

- 双栏左右模式兼容
- 四栏中线左右拖拽

如果同时把 `twoV` 也改成 `VSplitView`，改造面会扩大，收益却不直接对应当前需求。

### 步骤 6：不做分割比例持久化

本次明确不做：

- `WindowState` 新字段
- 运行时比例快照
- 项目切换恢复
- 应用重启恢复

这样可以避免：

- 解码兼容问题
- 旧状态迁移问题
- 保存节流逻辑额外噪音

## 8. 涉及文件范围

### 必改文件

- `Sources/mq-dir/MainWindowView.swift`

主要改动区域：

- `paneGrid`
- 如果需要，也可能抽出少量辅助 view，例如“左右列容器”

### 大概率不需要改的文件

- `Sources/mq-dir/BrowserPaneView.swift`

用途通常只是补最小宽度、间距、视觉细节，不应改业务逻辑。

## 9. 验收清单

### 9.1 双栏模式

- 切到 `twoH`
- 左右分隔线可拖动
- 拖动后左右 pane 内容正常显示
- 点击左 pane / 右 pane 都能正常更新焦点
- tab、搜索、空白区点击、文件选择行为不受影响

### 9.2 四栏模式

- 切到 `four`
- 中间竖线可左右拖动
- 上排与下排的竖线保持对齐
- 左列中的 `pane0`、`pane2` 同宽
- 右列中的 `pane1`、`pane3` 同宽
- 四个 pane 的焦点切换正常

### 9.3 边界场景

- 将中线向左拖到较窄位置，左列仍可用
- 将中线向右拖到较窄位置，右列仍可用
- 在某个 pane 打开 preview 后继续观察布局是否稳定
- 在拖动过中线后切换 `twoH <-> four`，界面不应错乱或崩溃

### 9.4 明确允许的现象

以下现象在本次范围内可以接受：

- 切换布局后分割位置回到系统默认分配
- 极窄宽度下出现横向滚动
- 切布局时不记住之前的拖拽位置

## 10. 不建议本次一起做的扩展项

下面这些内容建议后续单独做，不要和本次混在一起：

- 持久化 `twoH` / `four` 的左右分割比例
- 为四栏增加上下方向可拖拽分割线
- 给不同 layout 单独保存不同 split 比例
- 做复杂的 AppKit split controller 统一抽象
- 追加设置项让用户定义默认比例

原因很简单：这些都会把一次“容器层改造”升级为“布局系统升级”，范围和验证成本都会显著上升。

## 11. 最终建议

如果目标严格限定为“当前运行时，四栏中线能自由左右拖动，并兼容双栏”，那么推荐执行下面这个最小改动方案：

1. 只改 `MainWindowView.paneGrid`
2. `twoH` 改为 `HSplitView`
3. `four` 改为“外层 `HSplitView` + 左右列内部 `VStack`”
4. `twoV` 保持不动
5. 不新增持久化字段
6. 先完成基础拖拽，再根据实际表现决定是否补 `minWidth`

这个方案的优点是：

- 改动面最小
- 风险可控
- 很贴合当前需求
- 后续若你确认体验满意，再继续演进到“记住比例”也有自然的升级路径

## 12. 预期收益

完成后，用户能直接获得以下体验提升：

- 四栏模式中，上下两排共享一根真正可拖动的中线
- 双栏模式中，左右宽度调整更自然
- 主内容区的布局行为和侧边栏、pane 内 preview 一样，更接近原生 split 体验
- 后续如果要加“记住分割比例”，结构上也已经走在正确方向上

---

如果后续确认进入实现阶段，建议先做一个最小版本，只验证 `twoH` 与 `four` 的 split 结构是否稳定，再决定是否补充最小宽度保护和运行时比例桥接。
